# Методичка: Lab 2 — мониторинг Linux с VictoriaMetrics и Prometheus

Цель лабораторной — научиться получать метрики Linux, писать запросы PromQL и создавать правила оповещений (alerts).

Пойдём по шагам: сначала проверим сбор метрик, затем напишем три запроса, проверим их результаты и в конце создадим собственный alert.

## Что должно получиться

| Задание                                | Что будем использовать          |
| -------------------------------------- | ------------------------------- |
| 1. Загрузка CPU по каждому ядру        | `node_cpu_seconds_total`        |
| 2. Использование RAM в процентах       | `node_memory_*_bytes`           |
| 3. Запись на диск за последние 5 минут | `node_disk_written_bytes_total` |
| 4. Alert на выбор                      | Prometheus alerting rules       |

Важный момент: VictoriaMetrics не собирает системные метрики Linux самостоятельно. Для этого нужен экспортёр, обычно `node_exporter`, который отдаёт метрики, а VictoriaMetrics их периодически забирает (scrape).

Судя по твоей первой лабораторной, у тебя уже запущена VictoriaMetrics на порту `8428` с конфигурацией `prometheus.yml`. Начнём с проверки того, что настроено.

## Шаг 2. Если метрик нет — подключаем Node Exporter

Node Exporter собирает сведения о процессоре, памяти, дисках и других ресурсах Linux.

На Linux-машине, которую нужно мониторить, запусти:

```
docker run -d \
  --name node-exporter \
  --restart=always \
  --net=host \
  --pid=host \
  -v "/:/host:ro,rslave" \
  prom/node-exporter:latest \
  --path.rootfs=/host
```

Проверь, что экспортёр отвечает:

```
curl http://localhost:9100/metrics
```

В выводе должны встречаться метрики `node_cpu_seconds_total`, `node_memory_MemTotal_bytes` и другие.

Если VictoriaMetrics работает в другом контейнере или на другом сервере, адрес `localhost:9100` в конфигурации VictoriaMetrics использовать нельзя: это будет адрес самой VictoriaMetrics. Укажи IP Linux-машины с Node Exporter, доступный из контейнера VictoriaMetrics.

### Настраиваем сбор метрик

В файле `prometheus.yml` добавь или объедини с существующей конфигурацией следующий блок:

```
scrape_configs:
  - job_name: node
    static_configs:
      - targets:
          - '192.168.23.11:9100'
```

Здесь `192.168.23.11` — пример IP Linux-машины. Замени его на реальный адрес хоста с Node Exporter. Если `scrape_configs` уже есть, не добавляй второй одноимённый ключ, а дополни существующий список.

Конфигурация указывается в формате Prometheus, который VictoriaMetrics умеет использовать для сбора метрик.&#x20;

## Шаг 3. Определяем загрузку CPU по каждому ядру

### 3.1. Сначала изучаем исходную метрику

Выполни запрос:

```
node_cpu_seconds_total
```

Обрати внимание на метки `cpu` и `mode`.

- `cpu` — номер логического ядра.
- `mode` — состояние процессора: `idle`, `user`, `system`, `iowait` и другие.
- Значение метрики — накопленное время в секундах, проведённое в данном состоянии.

Это счётчик, поэтому его текущее значение не является процентом загрузки. Чтобы измерить загрузку, используем `rate()`, которая вычисляет среднюю скорость изменения счётчика за заданный интервал.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://prometheus.io\&sz=32)

Prometheus



### 3.2. Пишем запрос загрузки каждого ядра

```
100 * (
  1 - avg by (instance, cpu) (
    rate(node_cpu_seconds_total{mode="idle"}[5m])
  )
)
```

Нажми Execute.

Что делает запрос:

1. `rate(...[5m])` — оценивает скорость изменения счётчика за последние 5 минут.
2. `{mode="idle"}` — оставляет только время простоя процессора.
3. `avg by (instance, cpu)` — объединяет серии по каждому ядру и хосту.
4. `1 - ...` — вычисляет долю времени, когда процессор не простаивал.
5. `100 * ...` — переводит долю в проценты.

Результат — процент загрузки каждого логического ядра за последние 5 минут.

Например, если ядро загружено на 35%, его серия будет иметь значение около `35`.

Что зафиксировать в отчёте: запрос, скриншот результата и пояснение, почему используется `rate()`, а не текущее значение счётчика.

## Шаг 4. Определяем использование оперативной памяти в процентах

В задании указаны метрики `node_memory_*_bytes`. Для расчёта нам нужны две из них:

- `node_memory_MemTotal_bytes` — общий объём оперативной памяти.
- `node_memory_MemAvailable_bytes` — сколько памяти доступно для использования с учётом возможности освободить часть занятой памяти.

### 4.1. Проверяем исходные значения

Выполни по очереди:

```
node_memory_MemTotal_bytes
```

```
node_memory_MemAvailable_bytes
```

Результаты выражены в байтах.

### 4.2. Вычисляем процент занятой памяти

```
100 * (
  1 -
  node_memory_MemAvailable_bytes
  /
  node_memory_MemTotal_bytes
)
```

Например, результат `62` означает, что примерно 62% памяти сейчас занято с точки зрения выбранного определения доступной памяти.

Почему используется `MemAvailable`, а не `MemFree`? Linux активно использует свободную память для кеширования. Часть этой памяти может быть освобождена при необходимости, поэтому `MemAvailable` обычно лучше отражает реальную доступность RAM.

Что зафиксировать в отчёте: формулу, результат в процентах и краткое объяснение двух метрик.

## Шаг 5. Определяем количество байтов, записанных на диск за последние 5 минут

В задании указана метрика:

```
node_disk_written_bytes_total
```

Это накопительный счётчик общего объёма записи. Само по себе его значение показывает объём с момента запуска учёта, а не только за последние пять минут.

### 5.1. Смотрим, какие диски доступны

```
node_disk_written_bytes_total
```

Посмотри на метки `instance` и `device`. Они помогут определить хост и конкретное устройство — например, `sda` или `nvme0n1`.

### 5.2. Считаем объём записи за 5 минут

```
increase(node_disk_written_bytes_total[5m])
```

`increase()` вычисляет увеличение счётчика за указанный период с учётом сбросов счётчика.

Результат выражен в байтах и будет показан отдельно для каждого устройства.

Если нужно получить суммарный объём записи по всем устройствам каждого хоста:

```
sum by (instance) (
  increase(node_disk_written_bytes_total[5m])
)
```

Если нужно показать объём записи в гигабайтах, можно разделить результат на \\(1024^3\\):

```
sum by (instance) (
  increase(node_disk_written_bytes_total[5m])
) / 1024^3
```

Это будут гибибайты (GiB), хотя их часто называют гигабайтами.

Важный нюанс: сумма по всем устройствам может включать физические диски и устройства, лежащие поверх них, например виртуальные или RAID-устройства. Если требуется точный объём физической записи, нужно учитывать архитектуру хранения и не суммировать повторно одни и те же операции.

Что зафиксировать в отчёте: основной запрос с `increase()`, результат по дискам и объяснение, почему нельзя просто посмотреть текущее значение счётчика.

## Шаг 6. Создаём собственный alert

Для лабораторной предлагаю сделать оповещение о высокой загрузке оперативной памяти: если занято более 80% RAM в течение 5 минут, правило должно перейти в состояние `firing`.

Здесь важно различать два действия:

- Создать правило — описать условие в YAML.
- Выполнять правило — запустить компонент, который периодически вычисляет выражение и отслеживает срабатывание.

В твоей связке с VictoriaMetrics для выполнения правил используется `vmalert`. Отправка уведомлений, например в Telegram или по почте, дополнительно требует настроенного Alertmanager или другого поддерживаемого получателя.&#x20;

### 6.1. Создаём файл с правилом

В рабочем каталоге создай файл `alert.rules.yml`:

```
groups:
  - name: linux-alerts
    interval: 30s
    rules:
      - alert: HighMemoryUsage
        expr: |
          100 * (
            1 -
            node_memory_MemAvailable_bytes
            /
            node_memory_MemTotal_bytes
          ) > 80
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "High memory usage"
          description: "Memory usage is above 80% on {{ $labels.instance }}"
```

Разберём ключевые поля:

| Поле            | Значение                                   |
| --------------- | ------------------------------------------ |
| `groups`        | Группы правил                              |
| `name`          | Имя группы                                 |
| `interval: 30s` | Проверять условие каждые 30 секунд         |
| `alert`         | Имя оповещения                             |
| `expr`          | PromQL-условие срабатывания                |
| `for: 5m`       | Условие должно оставаться истинным 5 минут |
| `labels`        | Дополнительные метки оповещения            |
| `annotations`   | Человекочитаемое описание                  |

### 6.2. Запускаем vmalert

Если VictoriaMetrics запущена на Linux-хосте с опубликованным портом `8428`, можно использовать сетевой режим хоста:

```
docker run -d \
  --name vmalert \
  --restart=always \
  --network host \
  -v "$(pwd)/alert.rules.yml:/etc/vmalert/alert.rules.yml:ro" \
  victoriametrics/vmalert:latest \
  -rule=/etc/vmalert/alert.rules.yml \
  -datasource.url=http://127.0.0.1:8428
```

Команда предполагает, что файл `alert.rules.yml` находится в текущем каталоге, а VictoriaMetrics доступна на хосте по адресу `127.0.0.1:8428`. Если работаешь на macOS или в другой сетевой конфигурации, адрес источника данных нужно будет изменить.

### 6.3. Проверяем работу правила

Посмотри логи:

```
docker logs --tail=100 vmalert
```

Открой интерфейс vmalert:

`http://localhost:8880/`

В разделе правил проверь, загрузилась ли группа `linux-alerts` и отображается ли `HighMemoryUsage`.

Можно также проверить API правил:

```
curl http://localhost:8880/api/v1/rules
```

Состояния оповещения обычно проходят три стадии:

- `inactive` — условие не выполняется.
- `pending` — условие выполняется, но ещё не прошло 5 минут.
- `firing` — условие выполняется достаточно долго.

Если память занята меньше чем на 80%, оповещение останется `inactive`. Это нормальный результат, а не ошибка. Для лабораторной можно продемонстрировать правило на текущих показателях и объяснить ожидаемое поведение при превышении порога.

Документация: [Prometheus — Alerting rules](https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/?utm_source=chatgpt.com) и [VictoriaMetrics — vmalert](https://docs.victoriametrics.com/victoriametrics/vmalert/?utm_source=chatgpt.com).
